## Learning Objective

By the end of this lesson, you will be able to read a `composer.json` file, explain what its most important fields mean, and describe how it declares a project's dependencies.

## Explanation

Every Composer-managed project has a file called `composer.json` in its top-level folder. This file is written in **JSON** (JavaScript Object Notation), a text format for storing structured data with key-value pairs, arrays, and nested objects. Think of `composer.json` as the project's identity card plus its shopping list: it states the project's name and requirements, and it lists every external package the project needs.

The most common fields are:

- `name` — the project's unique name in `vendor/package` format, for example `"acme/blog"`. The **vendor** part identifies the publisher, and the **package** part identifies the project.
- `description` — a short human-readable summary of what the project does.
- `require` — an object that maps each needed package to an allowed version range, for example `"monolog/monolog": "^2.0"`. A **version constraint** like `^2.0` describes which releases are acceptable.
- `require-dev` — like `require`, but only for tools needed during development (test runners, debuggers), not in production.
- `autoload` — tells Composer how to map your own project's class names to files, so your classes load automatically.
- `scripts` — named shortcuts for commands you run often, such as running tests.

## Why It Matters

Without `composer.json`, there would be no reliable record of what your project depends on. A new team member or a production server would have to guess which libraries to download and which versions work together. With `composer.json` checked into version control, anyone can recreate the exact same setup with a single command, which is the foundation of reliable collaboration and deployment.

## Example

A small blog project needs a logging library to record errors and requires PHP 8.1 or newer. Its `composer.json` declares this information so Composer can install the right packages.

## Code

```json
{
    "name": "acme/blog",
    "description": "A small learning blog built with plain PHP.",
    "require": {
        "php": ">=8.1",
        "monolog/monolog": "^2.0"
    },
    "require-dev": {
        "phpunit/phpunit": "^10.0"
    },
    "autoload": {
        "psr-4": {
            "Acme\\Blog\\": "src/"
        }
    }
}
```

## Code Explanation

- `"name": "acme/blog"` gives the project a globally unique identifier following the `vendor/package` convention.
- `"require"` lists runtime dependencies: PHP itself (`>=8.1` means version 8.1 or newer) and the logging library `monolog/monolog` at version `^2.0`.
- `"require-dev"` lists `phpunit/phpunit`, a testing tool needed only while developing, so production servers can skip it.
- `"autoload"` with `psr-4` maps the `Acme\Blog\` class prefix to the `src/` folder, so `Acme\Blog\Post` loads from `src/Post.php` automatically.

## Common Mistakes

- **Editing `composer.lock` by hand.** The lock file records exact installed versions and is generated by Composer; you should only ever edit `composer.json` directly.
- **Putting development tools in `require` instead of `require-dev`.** This forces production servers to install testing tools they never use.
- **Forgetting the `php` version requirement.** Without it, Composer may install package versions that need a newer PHP than your server provides.

## Best Practices

- Commit `composer.json` (and `composer.lock`) to version control so every environment installs identical dependencies.
- Keep `description` accurate and up to date so other developers understand the project at a glance.
- Declare the minimum PHP version your code actually needs under `require` to catch incompatibilities early.

## Exercise

Write a `composer.json` for a project named `acme/shop` that requires PHP `>=8.2` and the package `symfony/console` at `^6.0`, with PHPUnit `^10.0` as a development-only dependency.

## Solution

```json
{
    "name": "acme/shop",
    "description": "A small learning shop project.",
    "require": {
        "php": ">=8.2",
        "symfony/console": "^6.0"
    },
    "require-dev": {
        "phpunit/phpunit": "^10.0"
    }
}
```

This declares the project identity, the runtime needs (PHP and the console component), and keeps the testing tool in `require-dev` where it belongs.
